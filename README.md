# rag-agent

**Живое демо:** https://rag-agent-liard-two.vercel.app
(фронт — Vercel, бэкенд — Render, база — Neon; архитектура и почему именно так — ниже)

Senior-уровневый (по объёму инженерных решений, не по объёму кода) пример
RAG + агента, написанный руками, без LangChain/LlamaIndex — чтобы под
каждой строчкой можно было ответить "почему так", а не "так сгенерировалось".

Это прямое продолжение конспекта: Часть 3 (голый RAG) → Часть 4 (апгрейды:
pgvector, реранкинг, hybrid search, eval) → Часть 5 (агент) → финальный шаг
из конспекта — RAG как **инструмент** агента, а не отдельная система.

## Труба (нарисуй это на доске на интервью)

```

```

## Почему так, а не иначе (вопросы, которые реально задают на технике)

**Почему pgvector, а не Pinecone/Qdrant/Weaviate?**
Не хотел городить отдельную инфраструктуру под vector search, когда
Postgres и так есть в стеке (aria, jobboard). pgvector даёт HNSW-индекс —
этого достаточно вплоть до миллионов векторов. Отдельную vector DB имеет
смысл брать, когда нужны фичи, которых у Postgres нет (например,
multi-tenant sharding из коробки на очень большом масштабе).

**Почему hybrid search (vector + BM25), а не просто эмбеддинги?**
Эмбеддинги ловят смысл ("сколько стоит" ≈ "какая цена"), но плохо ловят
точные токены — версии, коды ошибок, имена. BM25 — наоборот. Берём
кандидатов из обоих, объединяем, потом фильтруем реранкингом.

**Почему реранкинг отдельным шагом, а не сразу top-k от векторного поиска?**
Bi-encoder (эмбеддинги) кодирует вопрос и чанк НЕЗАВИСИМО — быстро,
масштабируется, но менее точно. Cross-encoder читает пару вместе — точнее,
но пересчитывать его на всей базе для каждого запроса нельзя (слишком
дорого). Поэтому: bi-encoder для recall (грубо, дёшево, много кандидатов),
cross-encoder для precision (точно, дорого, мало кандидатов).

**Чем агент отличается от RAG здесь конкретно?**
`rag.py::answer()` — фиксированный pipeline: всегда retrieve → generate,
без вариантов. `agent.py::run_agent()` — модель сама решает, вызывать ли
`search_documents`, `calculate`, оба, ни одного, и сколько раз (до
`MAX_STEPS`). RAG в этом проекте не исчез — он стал ОДНИМ ИЗ инструментов,
которые агент может вызвать по своему решению.

**Почему калькулятор через `ast`, а не `eval(expression)`?**
LLM генерирует строку, которую мы бы выполнили как код — классическая
инъекция (модель может "нафантазировать" вредоносное выражение, или его
туда подложит промпт-инъекция из документа). `ast`-парсер разрешает только
арифметику, ничего больше выполнить нельзя.

**Как измеряется качество?** (`src/eval.py`)
Два вопроса, две метрики: retrieval hit rate ("нашли ли мы вообще нужный
документ?") и faithfulness ("ответ следует строго из найденного контекста,
без отсебятины?", проверяется отдельным вызовом LLM-судьи). Без этого
файла проект — "вроде работает", с ним — можно показать число.

Реальный прогон против Neon: **retrieval hit rate 100%, faithfulness 75%**
(4 вопроса). Число не подкручено — "провал" faithfulness это ловушка-вопрос
("какая погода в Москве завтра?"), на который модель ЧЕСТНО ответила "не
знаю", но LLM-судья всё равно поставил FAIL, хотя в его собственном промпте
написано, что честный отказ = PASS. Это отдельная, отличная от retrieval/
generation проблема — калибровка самого судьи, — и хороший пример того,
почему "есть eval" не значит "числу можно слепо верить": судью тоже нужно
валидировать.

**Почему две реализации эмбеддингов/реранкинга (local и Cohere)?**
Это НЕ два случайных варианта — это конкретный компромисс self-hosted vs
managed inference, найденный руками, а не выбранный заранее:
sentence-transformers (bi-encoder + cross-encoder) вместе весят на диске
~930MB и держат в памяти процесса ~1.3GB RSS (проверено локально через
`ps`). На своей машине это бесплатно и ок. На Render free/starter tier
(512MB RAM) это OOM. Решение — не "уменьшить модель" (потеряли бы качество
на русском тексте, ради которого модели вообще меняли на мультиязычные),
а вынести инференс наружу: Cohere Embed + Rerank API, HTTP-вызов вместо
локальной модели. Переключается одной env-переменной `USE_COHERE`, весь
остальной код (retrieval.py, ingest.py) не знает и не должен знать, какой
бэкенд активен — см. `src/embeddings.py`.

## Структура

```
rag-agent/
├── data/*.txt              # исходные документы (пример: внутренние доки вымышленной компании)
├── db/schema.sql            # справочная структура таблицы chunks (реально создаётся динамически, см. db.py)
├── render.yaml                # Render Blueprint для деплоя API
├── web/                         # Next.js чат-фронт (деплоится на Vercel отдельно)
├── src/
│   ├── config.py         # все параметры + переключатель local/Cohere бэкенда
│   ├── db.py              # тонкий слой поверх psycopg, без ORM
│   ├── chunking.py        # текст -> чанки с overlap
│   ├── embeddings.py      # эмбеддинги/реранкинг: local (sentence-transformers) или Cohere API
│   ├── ingest.py           # data/*.txt -> чанки -> эмбеддинги -> Postgres
│   ├── retrieval.py        # hybrid search (vector + BM25) + rerank
│   ├── rag.py               # чистый RAG: retrieve + generate, без агента
│   ├── tools.py              # инструменты агента: search_documents, calculate
│   ├── agent.py               # многошаговый tool-use цикл поверх Groq
│   ├── eval.py                 # retrieval hit rate + faithfulness (LLM-judge)
│   └── api.py                   # FastAPI: /agent/ask, /rag/ask, CORS для фронта
├── requirements.txt         # база, без torch — то, что ставится на Render
└── requirements-local.txt    # requirements.txt + sentence-transformers для self-hosted режима
```

## Setup (локально, self-hosted модели)

```bash
# Postgres + pgvector уже подняты локально (brew, postgresql@17, база rag_agent)

cp .env.example .env
# вписать свой GROQ_API_KEY в .env; USE_COHERE не трогать (по умолчанию false)

python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements-local.txt

python -m src.ingest              # построить индекс из data/*.txt (создаст таблицу сам)

python -m src.rag                 # чистый RAG, один вопрос в интерактиве
python -m src.agent               # агент с инструментами
python -m src.eval                # прогнать eval-набор, увидеть метрики

uvicorn src.api:app --reload      # HTTP API
```

## Деплой (Render + Neon + Vercel)

Живая версия использует Cohere вместо self-hosted моделей (см. раздел про
компромисс выше) и облачный Postgres вместо локального.

1. **Neon** (Postgres с pgvector) — провизионится через Vercel Marketplace
   (`vercel integration add neon`) или напрямую на neon.tech. Получаешь
   `DATABASE_URL`.
2. **Render** — подключи GitHub-репо, Render подхватит `render.yaml`.
   Впиши секреты в дашборде: `GROQ_API_KEY`, `COHERE_API_KEY` (бесплатный
   trial на cohere.com), `DATABASE_URL` (из Neon), `ALLOWED_ORIGIN`
   (домен фронта на Vercel, после его деплоя).
3. Прогони `python -m src.ingest` один раз против Neon (например, через
   Render Shell) — наполнит облачную базу.
4. **Vercel** — `web/` деплоится отдельным проектом, env `NEXT_PUBLIC_API_URL`
   указывает на Render-сервис.

## Что дальше (следующий уровень апгрейда)

- Заменить golden set в `eval.py` на 30-50 размеченных пар — 4 вопроса
  показывают метод, не дают статистически значимого числа.
- Добавить streaming в `agent.py` (Groq поддерживает `stream=True`) — сейчас
  ответ агента приходит целиком, для чат-интерфейса нужен токен-за-токеном.
- Заменить `MAX_STEPS`-обрыв на что-то умнее — например, модель, зациклившаяся
  на одном и том же tool call с одинаковыми аргументами, стоит останавливать раньше.
- Multi-tenant: сейчас все чанки в одной таблице без разделения по
  пользователю/организации — в реальном продукте нужен `tenant_id` и фильтр
  в каждом запросе retrieval (иначе один клиент увидит документы другого).
